# PEELBEAST 전체 개발문서 v0.8

## 0. 문서 목적
이 문서는 현재 프로토타입의 상태, 버전별 구현 범위, 향후 개발 항목, 전투/조작감 설계, 최종 제품 방향을 한 번에 정리한 마스터 문서다.

---

## 1. 프로젝트 한 줄 정의
**PEELBEAST**는 종이 공예 감성의 파츠 조립형 턴제 로그라이크다. 플레이어는 머리/손/코어/장신구 파츠를 조합해 빌드를 만들고, 전투 중 파츠가 실제로 박리되거나 복구되며, 이벤트/상점/엘리트/보스를 포함한 한 런을 진행한다.

---

## 2. 현재 버전 상태 요약
### v0.8의 목표
- 단순 전투 샘플이 아니라 **한 판의 게임 흐름**이 실제로 보이는지 검증
- 조립 → 노드 진행 → 전투 → 보상/상점 → 보스까지 최소 루프 연결
- 파츠 조합이 UI 장식이 아니라 전투 규칙과 실제 비주얼에 모두 반영되는지 검증

### v0.8 현재 구현 범위
- 4개 파츠 슬롯 조립
- 파츠별 스탯/액티브/패시브 반영
- 턴제 전투
- 적 의도 큐 표시
- 파츠 박리 및 재부착
- 일반 전투 / 엘리트 / 보스 2페이즈
- 이벤트 노드
- 상점 노드
- 스크랩 자원
- 스테이지 모드(리릭) 누적
- HP/Glue 일부 캐리오버
- 2개 루트

### 아직 없는 것
- 애니메이션/이펙트의 고도화
- 사운드
- 데이터 저장/로드
- 다수의 적 풀 / 파츠 풀 / 이벤트 풀
- 정식 난이도 밸런싱
- 메타 성장
- 모바일 전용 UX

## 4. 현재 시스템 상세
### 4.1 조립 시스템
슬롯은 4개다.
- Head
- Hand
- Core
- Trinket

각 슬롯은 다음을 가진다.
- 시각 레이어
- 스탯 변화
- 액티브 스킬 1개
- 패시브 1개
- 박리 가능 여부

#### 조립 반영 방식
1. 조립 변경 시 즉시 스탯 재계산
2. 조립 변경 시 액션 패널의 스킬 변경
3. 전투 중 슬롯이 박리되면 해당 파츠의 스탯/스킬/패시브가 즉시 빠짐
4. 복구되면 다시 반영
5. 히어로 비주얼에서도 레이어가 실제로 바뀜

### 4.2 전투 시스템
전투는 1:1 기반 턴제다.

#### 플레이어 기본 행동
- Peel Strike: 기본 공격
- Guard: 방어
- Repair: HP/Glue 회복, 일부 빌드에서 복구 지원
- Press: 쿨다운 압축 + Glue 회복

#### 파츠 스킬 예시
- Toast Helm: Copy Spark
- Scissors: Scissor Flurry
- Pencil Spear: Pin Thrust
- Umbrella Hook: Umbrella Bastion
- Tape Roll: Patch Loop
- Coffee Cup: Coffee Overclock
- Bread Patch: Mending Patch

#### 상태/수치 축
- HP
- Glue
- Block
- Focus
- Drift
- Bind
- Haste
- Pinned
- Fragile
- Frazzle
- Ink Tide

### 4.3 박리 시스템
이 게임의 핵심 차별 포인트다.
- 적 공격은 단순 데미지뿐 아니라 특정 슬롯을 벗겨낼 수 있다.
- 슬롯이 박리되면 해당 파츠의 성능이 사라진다.
- 전투 중 복구 액션이나 파츠 스킬로 되붙일 수 있다.
- 즉, 이 게임은 “HP가 깎이는 것”과 “빌드가 무너지는 것”이 동시에 긴장 요소다.

### 4.4 노드 시스템
현재 노드 타입은 다음과 같다.
- Combat
- Event
- Shop
- Elite
- Boss

#### Event 반영 방식
이벤트 선택지는 즉시 런 상태에 적용된다.
- Scrap 획득
- HP/Glue 회복
- 특정 리릭 획득
- 리스크를 감수하고 더 큰 보상 획득

#### Shop 반영 방식
스크랩으로 다음을 구매한다.
- 리릭
- 즉시 회복 서비스
- 다음 전투 보강 서비스

#### Carry Over
전투 종료 후 남은 HP/Glue는 완전히 초기화되지 않고 다음 노드로 일부 이어진다.
이 구조는 한 판 전체의 긴장감을 만든다.

## 5. 전투 조작감 설계
### 5.1 조작의 기본 방향
이 게임은 실시간 액션이 아니라 **빠른 입력이 가능한 턴제**를 지향한다.
핵심은 “복잡한 계산”보다 “한 턴 안에 선택지가 명확하게 읽히는 것”이다.

### 5.2 기대 조작감
- 버튼을 눌렀을 때 즉시 결과가 보여야 함
- 적 의도가 먼저 공개되어 있어 판단이 가능해야 함
- 파츠 박리 시 시각 변화가 분명해야 함
- 스킬 쿨다운과 상태 변화가 UI에서 바로 읽혀야 함
- 로그는 세부 설명용, 핵심 정보는 바/칩/배지에서 먼저 보여야 함

### 5.3 현재 반영된 조작감 요소
- 즉시 반응형 버튼 구조
- 적 의도 큐 표시
- 스킬별 쿨다운 표시
- 파츠 박리 상태 표시
- 전투 로그 피드백
- 리릭/스크랩/노드 진행 정보 표시

### 5.4 앞으로 더 넣어야 할 조작감 요소
1. **히트 연출**
   - 피격 시 짧은 흔들림
   - 피해 숫자 플로팅
   - 박리 시 종이 찢김 연출
2. **상태 강조**
   - Bind, Pinned, Ink 상태를 아이콘으로 직관화
3. **선택 피드백 강화**
   - 버튼 hover/press 애니메이션
   - 턴 종료 전 예상 변화 미리보기
4. **적 의도 해석 강화**
   - 단순 텍스트 외 색상/위험도 표시

## 6. 앞으로 넣어야 되는 내용과 반영 방식
### 6.1 전투 쪽 우선순위
#### A. 애니메이션/연출
- **무엇을 넣나**: 공격 타격감, 회복 연출, 박리 연출, 스킬별 특수 연출
- **어떻게 반영하나**: CSS 애니메이션 + JS 클래스 토글 + 숫자 오버레이

#### B. 적 다양화
- **무엇을 넣나**: 적 8~12종, 보스 3~4종
- **어떻게 반영하나**: `ENCOUNTERS`, `INTENT_LIBRARY` 확장 + 아트 에셋 추가

#### C. 밸런싱
- **무엇을 넣나**: 파츠별 승률 차이 조정, 전투 길이 조정
- **어떻게 반영하나**: 수치 테이블 분리, 전투 로그 기반 플레이테스트

### 6.2 런 구조 쪽 우선순위
#### A. 이벤트 풀 확대
- **무엇을 넣나**: 선택지 15개 이상
- **어떻게 반영하나**: 데이터형 이벤트 JSON 구조화

#### B. 상점 고도화
- **무엇을 넣나**: 파츠 구매, 임시 버프, 소비 아이템
- **어떻게 반영하나**: `SHOP_POOL` 확장 + 인벤토리 슬롯 추가

#### C. 노드 시각화
- **무엇을 넣나**: 미니맵/루트 그래프
- **어떻게 반영하나**: 별도 route canvas 또는 SVG/HTML 레이아웃

### 6.3 메타 구조
#### A. 언락 시스템
- 특정 보스 처치 시 신규 파츠 언락
- 런 누적 조건으로 신규 이벤트/적 언락

#### B. 컬렉션
- 파츠 도감
- 적 도감
- 조합 프리셋 저장

#### C. 장기 플레이 보정
- 메타 성장 수치를 크게 두지 않고, 해금 중심 구조 권장

## 7. 최종적으로 나와야 되는 방향
### 7.1 제품 방향
최종 제품은 “가볍게 시작하지만 빌드 고민이 깊은 귀여운 파츠 조립형 로그라이크”여야 한다.
핵심은 아래 4개다.
1. **파츠 조합의 재미**
2. **전투 중 파츠가 실제로 망가지는 긴장감**
3. **짧은 런 단위 반복 플레이**
4. **시각적으로 기억나는 종이 공예 감성**

### 7.2 러닝타임 목표
- 1런: 15~25분
- 튜토리얼 제외 첫 승리 목표: 20~40분 내 접근 가능
- 너무 긴 런보다는 반복 실험이 쉬운 구조 권장

### 7.3 플랫폼 방향
1순위: 웹/데스크톱 프로토타입 검증
2순위: 모바일 대응 UI 재설계
3순위: 패키지형 앱 또는 스팀급 소형 게임 전환 검토

### 7.4 콘텐츠 목표치 예시
- Head 파츠 8종
- Hand 파츠 8종
- Core 파츠 8종
- Trinket 파츠 8종
- 일반 적 10종 내외
- 엘리트 4종
- 보스 3종 이상
- 이벤트 20종 이상
- 리릭 25종 이상

## 9. 구현 파일 구조 권장
- `index.html` : UI / 렌더 구조
- `assets/` : 이미지 에셋
- `data/parts.json` : 파츠 데이터
- `data/enemies.json` : 적/의도 데이터
- `data/events.json` : 이벤트 데이터
- `data/relics.json` : 리릭 데이터
- `src/runState.js` : 런 상태
- `src/battle.js` : 전투 규칙
- `src/render.js` : 화면 렌더링
- `src/effects.js` : 연출 / 이펙트

현재는 단일 HTML 중심이지만, 다음 단계부터는 데이터/로직 분리를 권장한다.

---

## 10. 정리
v0.8은 “전투 샘플”이 아니라 **최소한의 실제 게임 흐름**을 보여주는 버전이다.
지금부터의 핵심은 기능을 무한히 추가하는 것이 아니라,
- 어떤 빌드가 재미있는지
- 파츠 박리 메커니즘이 실제 차별점으로 느껴지는지
- 15~25분짜리 한 런이 완성도 있게 돌아가는지
를 검증하는 쪽이다.
